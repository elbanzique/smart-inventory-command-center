# Smart Inventory Command Center

An end-to-end logistics analytics platform built for **NovaLog Distribution**,
a fictional e-commerce logistics company with 3 warehouses, 50 suppliers,
5,000 products, and ~100,000 customer orders.

This project simulates a realistic business dataset and builds a full
analytics pipeline — from raw data generation through SQL analysis to a
Power BI dashboard — to answer the operational questions a supply chain
data analyst is asked in practice.

## Business questions answered

- Which warehouse performs best?
- Which products generate the most revenue?
- Which SKUs are at risk of stockout?
- Which suppliers are unreliable?
- How much inventory value is tied up in dead stock?
- Which products should be reordered?

## Tech stack

- **SQL (SQLite)** — schema design, analytical queries
- **Python / Pandas / NumPy** — data generation, transformation, analysis
- **Matplotlib** — exploratory visualization
- **Power BI** — final interactive dashboard
- **Git & GitHub** — version control

## Running the full pipeline

Each stage reads the previous stage's output, so run them in order:

```bash
python -m src.data_generation.generate_all   # 1. synthetic CSVs -> data/raw/
python -m src.etl.load_to_db                 # 2. build SQLite DB, verify FK integrity
python -m src.analysis.run_queries           # 3. run the 6 SQL business questions -> data/processed/
python -m src.analysis.generate_report       # 4. ABC/dead-stock/supplier analysis -> reports/
python -m src.etl.export_for_powerbi         # 5. star-schema export -> data/powerbi_export/
```

Every step prints its own validation report and fails loudly (non-zero
exit / raised exception) if something's wrong, rather than silently
producing bad output. Everything is seeded (`config.RANDOM_SEED`), so
re-running the whole pipeline from a clean checkout reproduces
byte-identical results.

Run the test suite with:

```bash
pytest          # 36 tests: generation, ETL/schema, SQL queries, star-schema export
```

## Power BI dashboard

`.pbix` is a proprietary Windows-only binary format with no supported
programmatic authoring path, so it isn't generated by this pipeline.
What *is* prepared: the full dimensional (star schema) model
(`src/etl/export_for_powerbi.py`), the complete DAX measure library
(`powerbi/measures.dax`), and a step-by-step build spec
(`docs/powerbi_guide.md`) covering relationships, model settings, and a
page-by-page report design. Building the report from these takes about an
hour in Power BI Desktop.

## Final documentation: UML diagrams & technical report

- **`docs/diagrams/`** — three UML diagrams, written as PlantUML source and

  regenerate them after an edit.
- **`docs/report/report.pdf`** — a 23-page LaTeX technical report covering
  architecture, the data model, methodology (including the calibration
  strategy and both bugs below, told as a full postmortem with before/after
  tables), the SQL and Pandas analysis results, the Power BI design, the
  test suite, and honestly-scoped future extensions. Source is
  `report.tex`; rebuild with `cd docs/report && make`.

## Notable engineering decisions & bugs caught along the way

Worth reading if you want the "why" behind this project rather than just
the "what" — these are documented in detail in `docs/architecture.md` and
`docs/data_dictionary.md`, and referenced directly in code comments:

- **Reference-informed simulation.** Synthetic data isn't generated with
  naive uniform randomness — distributions (supplier reliability,
  on-time-delivery rate, revenue concentration, seasonality) are calibrated
  against published statistics from the DataCo Smart Supply Chain dataset.
- **Two data-realism bugs were found and fixed during Phase 5, not before:**
  1. *Inventory thresholds disconnected from demand.* `safety_stock` was
     originally sized from an arbitrary popularity-rank formula unrelated to
     actual sales velocity, producing a nonsensical 0.04x inventory turnover
     and a $228M "dead stock" figure that had passed every validation check
     I'd written. Replaced with the standard
     `lead_time_demand → safety_stock → reorder_point` formulas tied to
     real per-SKU demand.
  2. *RNG seed reuse silently correlated two independent tables.* Every
     generator module drew from the same random stream, which — because of
     how inverse-CDF sampling works — made each order's month and its line
     count perfectly rank-correlated, manufacturing a phantom 2.4x revenue
     "growth trend" between 2024 and 2025. Fixed with independent named
     random streams (`np.random.SeedSequence`).

  Both bugs passed every *single-table* check (marginal distributions were
  genuinely correct in each case) — only *cross-table* checks caught them.
  Regression tests for both now live in `tests/test_data_generation.py`.
- **The supplier scorecard is validated against a hidden ground truth.**
  It's built entirely from observed purchase-order behavior (never reading
  the seed reliability score used only for data generation), then
  correlated against that hidden seed afterward: r = 0.838, showing the
  methodology recovers genuine reliability signal rather than fitting noise.
